# UX and Interaction Specification

## Welcome screen and character creator

The browser first requires a local account sign-in or account creation, then opens to a full-viewport, dark navy dashboard with restrained cyan and violet lighting and a faint, low-contrast perspective-grid overlay. Accounts use a username and password; the password is stored as a scrypt hash, and a signed-in user sees only their own projects. A sign-out control is available on the dashboard and in the editor. A left navigation rail contains Home, Projects, Models, Tools, Settings, and a visually separated Help item; unavailable destinations are visibly disabled. The top bar shows API readiness and the signed-in username. The main hero presents the **CREATE. COLLABORATE. CRAFT.** identity and supported draft-first character workflow beside the supplied brand illustration. It describes character creation as the current supported workflow and frames worlds, animation, materials, and other content types as broader product vision rather than available features. The project-backed AI Assistant includes starter suggestions that either open character setup or fill the prompt without sending it, and can be collapsed to a compact launcher or expanded in place.

The dashboard has five rearrangeable cards: the welcome hero, AI assistant/chat, a clearly marked illustrative **Fantasy Realm** visual concept that is not a saved project, a draft/compile workflow explainer, and Recent Projects populated only from the API. On desktop, pair the hero and brand illustration with the workflow explainer in the upper row; align Chat with Canvas, Recent Projects, and New Projects as three balanced cards below. This grouping makes the workflow card support the introduction and lets the dashboard continue naturally into usable project actions. Drag a card by its grip or use its move-up/move-down controls; the chosen order is saved in browser-local storage and can be reset from the top bar. The layout remains responsive as cards move. The lower cards have full-card actions: the concept starts the real character setup flow, the workflow card fills the assistant prompt, and Recent Projects opens a saved project while preserving its individual project actions. Recent projects show up to three real saved projects with their model and draft/compiled state and expose loading and error states rather than fabricated projects, previews, or dates. The workflow panel describes existing draft-preview and explicit compile behavior.

At tablet widths, the navigation becomes a horizontal icon bar; the hero and workflow share the top row, with the assistant and project cards arranged beneath them. The dashboard scrolls vertically when the available height cannot fit those rows, rather than clipping or overlapping cards. On narrow screens, compact hero artwork and copy stack above the workflow, assistant, and project panels, with vertical scrolling retained to keep controls readable without oversized fixed card heights. The assistant is part of the page layout rather than a floating window.

On a 1365×768 desktop, keep the 158px navigation rail distinct from the main dashboard. Place the welcome copy and illustration across the left portion of the upper row, with the draft-first workflow card at the right. Align Chat with Canvas, Recent Projects, and New Projects in a lower row beginning around 420px from the top and ending about 58px above the viewport bottom. Use roughly 25px of left and 17px of right dashboard inset; keep the cards similar in width and around 250–275px tall. Keep the hero illustration within its upper row so it does not overlap the lower cards. At short desktop heights, compact the hero typography, illustration, workflow details, and lower-card content so all five cards remain visible in the same viewport without dashboard scrolling. When browser zoom reduces the actual visible viewport below the desktop breakpoint while the layout viewport remains large, use the visual viewport dimensions to fit the dashboard into that visible area. On narrow mobile screens, preserve readable controls and allow vertical scrolling rather than shrinking the page to an unusable scale.

The welcome screen does not imply that unsupported modeling features are available. A first chat prompt stays in the composer while the user chooses an installed model; only after the user confirms project creation is the draft/plan created and the prompt sent through the project-scoped AI endpoint. Typing or opening the page never creates a project or starts Blender. Starting a character opens the installed-model chooser, with Basic (CC3 Female) recommended and Advanced (CC3+ Female) offered where available. Creating a project enters the character workspace and creates a saved draft/plan; it does not compile geometry. Opening a saved project is an explicit action. A Home action returns to the welcome screen only when draft edits are saved.

The create-project and character chooser dialogs use the dashboard's navy, cyan, and violet palette. The character chooser follows the supplied compact two-column reference: the title, character name (the saved project name), and installed base-model choices on the left; the supplied brand illustration and an accurate draft/approval/compile summary on the right. The reference's style and personality controls are not implemented: show any visual stand-ins as clearly unavailable, noninteractive placeholders, and keep the personality field and advanced options disabled. Do not imply that these choices affect a character. Keep the real model selection, name, and create action visible; on narrow screens, hide the decorative and unavailable placeholder areas and keep the real project controls usable without an internal scrollbar.

The current startup asset is a rigged CC3 base, not the armored fantasy character in the visual reference. Do not imply that clothing, skin, markings, or other unsupported content is present or editable. Show only manifest-backed morph controls; show the installed body/head preset library only when the compatible CC5/CC3+ model is selected.

## Desktop layout

- **Three-column editor:** the desktop character editor uses a persistent left Chat panel (about 15% of the window), a central 3D viewport, and a right character editor (about 44%). Keep the chat panel in its own reserved, full-height layout column so it never overlays the character or viewport; messages scroll independently. It can be collapsed to a narrow launcher. The top bar spans the workspace with the C3Canvas wordmark, explicit New/Open Project actions, disabled undo/redo and Play, and **Save / Compile**. Open Project shows an accessible saved-project list and is disabled when no other projects exist. Save / Compile remains gated on plan approval, a saved draft, and Blender availability.
- **Viewport:** use the remaining central width for the live browser preview, with a dark navy studio, a soft blue-violet radial light, and the actual selected character asset. Keep the viewport interactive and retain its camera, fullscreen, projection, and lighting controls. Place display controls along the top edge of the viewport, never over the lower edge where they obscure the character. Do not substitute reference-image clothing or body geometry for the installed character.
- **Right editor:** align the six Morph, Eyes, Skin, Clothing, Extras, and Advanced tabs with the top bar. The first five select their existing customization categories; Advanced opens the existing advanced morph mode. Below them, show the manifest-backed anatomy list alongside the morph search, filters, library views, and compact three-column morph cards. Selected morph details, slider, reset, and related controls remain available below the library; installed body/head presets may be shown in a separate Active Presets row with a working add/remove action. Do not invent category assets, presets, or clothing. The CC3+ Ears category offers the **Elven Ears** preset only when its verified native controls are installed; it changes draft morph values and remains editable with standard controls.
- **Responsive sizing:** users can resize the right editor from its left edge by pointer or keyboard while preserving at least 320px for the viewport. The top bar remains 64px tall on desktop. At widths from 761px through 1100px, keep the viewport and editor in independently sized side-by-side regions; at widths of 760px and below, use a 52px header, collapse Chat to its launcher by default, and stack the viewport and editor in the remaining height. Reopening Chat gives it a compact, scrollable row without overlapping the sidebar. Keep the fixed-height category tabs horizontally scrollable, the morph anatomy selector horizontally scrollable, and morph controls vertically scrollable within the editor without page-level overflow; pin the morph title, control count, and draft status while scrolling. Center viewport loading and import status overlays over the available canvas area. When browser zoom makes the visual viewport narrower than the layout viewport, fit the editor shell to the visible area and stack the viewport and editor there instead of clipping desktop columns; keep Chat collapsed by default and its launcher available. Retain a full-width composer above its action buttons when Chat is reopened.
- Hair generation and hairstyle preview/attachment are not currently supported; do not show a Hair category or imply that a hairstyle can be previewed, saved, or compiled.
- If Blender is unavailable, show a persistent workflow status explaining that compilation is disabled while the browser draft and saved choices remain available. Disabled compile actions explain whether Blender, plan approval, or draft saving is the blocker; API connection errors direct users to restore the API, not Blender.
- Initial API, saved-project, and character-catalog loading failures expose targeted retry actions in place. Retrying reloads workspace metadata without creating, deleting, or changing project data.
- Eye and skin catalog errors in the editor expose their own in-place retry controls; retrying only reloads compatible asset metadata and does not alter saved draft selections.
- If manifest-backed morph controls fail to load or an empty catalog is returned for a supported model, show the error with a retry action. Retry reloads controls for the selected asset without changing its draft morph values.
- A failed 3D character, morph, or eye preview provides an in-place retry that clears cached failed GLTF requests and reloads the same selected preview without changing project draft state.
- The project Workflow section lists attached reference filenames and dimensions, clearly states they are stored but not visually analyzed or used to infer character details, and provides add/remove actions with visible upload progress. Never show reference content as if it were analyzed or use it to imply modeled details.
- The header Undo/Redo controls and Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, and Ctrl+Y shortcuts are explicitly scoped to morph-value edits (sliders, morph resets, the Elven Ears preset, and applied assistant morph proposals). A continuous slider gesture is one undo step. Shortcuts do not intercept typing or native undo in text fields, textareas, or sliders. They do not undo appearance choices, paint, or compiled Blender operations. Uncompiled changes autosave to the draft; compiled morph edits remain local until the user chooses **Save changes to Blender**.
- **Viewport controls:** use Blender-style navigation: middle-drag orbits, Shift+middle-drag pans, Ctrl/Cmd+middle-drag zooms, and the wheel zooms. Holding the Pan toolbar button requests native browser pointer lock on the viewport canvas; relative mouse movement pans until the left button is released or pointer lock is interrupted. Right-drag is not assigned a camera action. A compact lower-center toolbar resets the camera, enters fullscreen, switches perspective/orthographic projection, and selects cool/warm studio fill lighting. Recording is visibly unavailable. Do not show the retired Camera/Pose overlay.
- **Ear morph hierarchy:** CC5/CC3+ Ears opens to grouped cards rather than a flat list. The groups are Ear Tip (8), Earlobe (28), Ear Center (6), Ear Rim (43), Ear Rim Details (57), Ear Inner Structure (25), Ear Angle (14), Ear Depth (23), Ear Width (4), Ear Height (5), Ear Size (4), Ear Shape (4), and Other (3). In the pinned CC5/CC3+ manifest, the groups are Overall Body (20), Neck & Nape (27), Shoulders (8), Chest & Breasts (10), Abdomen & Waist (3), Hips & Glutes (6), Limbs (4), Eyes & Eye Orbit (32), Tearline (20), Teeth (24), Face Detail (1), and Other Body Controls (25), covering all 180 controls currently classified in the existing Body category. The legacy category includes eye-orbit, tearline, and dental controls; they remain available and are grouped by their names without changing morph data or deformation logic. CC3 Female and Male use the same grouping and omit the existing hidden torso-length control. Group cards respect All/Favorites/Recent and type filters. Search spans Body groups and other anatomy categories; Body search results show their group, and selecting a result opens its group and control.
- **Head morph hierarchy:** Head opens to Overall Head (13), Skull & Cranium (49), Forehead (24), Head Proportions (13), and Head Orientation (4), accounting for all 103 controls in the pinned CC5/CC3+ manifest. The Brow group contains the protruding-brows preset; the Face Shape Presets group contains named whole-face silhouette presets. CC3 Female and Male each expose five brow controls. - **Eye morph hierarchy:** Eyes opens to Eye Position & Proportions (62), Inner & Outer Corners (24), Eyelids & Folds (91), Eye Expression (15), Upper Eyelashes (48), Lower Eyelashes (30), General Eyelash Controls (7), Under-Eye & Eye Bags (12), Eye Socket & Orbit (19), Iris & Pupil (3), Eye Shape (9), and Eyelid Style Presets (2). CC3 Female and Male each have 14 Eyes-category controls; their available eyelash, eyelid, position, and proportion controls remain organized by the same classifier. - **Remaining morph hierarchies:** Nose, Mouth, Arms, Hands, Legs, Feet, and Misc open to compact group cards; the groups are generated only when they contain controls for the selected character. The pinned CC5/CC3+ counts are Nose: Nostrils & Nasal Openings (96), Nose Tip (26), Bridge & Overall Shape (67); Mouth: Mouth Shape & Expression (124), Lips (45), Jaw & Chin (94), Cheeks & Dimples (110), Teeth (56), Tongue (7); Arms: Upper Arm (2), Forearm (7), Elbow (3), Wrist (4), General Arm Shape (10); Hands: Fingers (2), Palm (4), Nails (4), Overall Hand (4); Legs: Thigh (3), Knee (14), Calf & Shin (1), Ankle (1), Overall Leg (6); Feet: Foot Shape (6), Toes (7), Heel (3); and Misc: Dental Details (140), Eyeballs (17), Eye Orbit (21), Tearline & Tear Duct (28), Numbered Controls (180), Body Details & Poses (16), Face & Head Details (3), Base Shapes & Resets (9). These groups account for all 1,120 controls in those seven existing categories. - **Tablet and mobile:** keep the workspace within the viewport and stack the 3D viewport above the editor without page-level scrolling. The editor has one primary scroll region; its category tabs stay visible and scroll horizontally when needed. The anatomy navigation also scrolls horizontally on compact layouts, while morph cards use a responsive grid with consistent card heights. A horizontal keyboard-operable divider resizes the viewport and editor, and Viewport/Balanced/Editor controls provide quick size presets; the existing vertical divider remains available on desktop. Keep viewport navigation at the canvas edge and the display toolbar at its lower-right edge so controls do not cover the character. Use a compact icon navigation rail at tablet and phone widths, preserve touch targets, and offset the assistant launcher from the display toolbar so they remain independently tappable.

## Project and approval flow

1. Startup loads the welcome screen, project summaries, and installed-model catalog without mounting the 3D viewport or downloading the character preview. The model preview and manifest-backed morph controls load after the user creates or opens a project. The larger editable morph preview is loaded only when the user adjusts a control.
2. The welcome screen’s **Start a new character** action opens project setup directly at the installed-model chooser. The user selects an installed model; the API creates a project and reviewable plan without requiring Blender or importing geometry.
3. The selected model's browser preview is available in the draft. Slider values are autosaved as a complete manifest map and draft revision; eye and preset choices are also persisted as draft appearance. CC3, eye, and verified CC5 proxy changes preview locally. If the optional CC5 proxy is unavailable, its sliders remain disabled rather than invoking Blender for a preview.
4. The user explicitly approves the plan. Approval is enforced by the API but does not start Blender or create geometry.
5. A separate **Save / Compile** action requires plan approval and Blender availability. The worker imports the selected pinned source, applies the saved slider map and preset, and imports the selected eye in one operation. Draft editing does not import geometry or start Blender. After compilation, the viewport switches to the saved GLB; later scene changes require explicit, supported worker operations.
6. The reference-plan card clearly states that reference images are stored but not analyzed.

Opening a saved project is an explicit action from the Open Project header button; the application does not automatically restore a project or mutate saved data on launch. Project approval and Blender build actions remain in the Scene workflow inspector.

## Assistant

The AI Assistant is open on the welcome screen and remains available in the character workspace. On the welcome screen, a first prompt is held until the user selects a model and explicitly creates a draft project; it is then sent to the project-scoped chat API. In the workspace, the assistant retains chat history and supports resizing and repositioning while open. Requests use the configured local Copilot bridge; errors are explicit, and the UI never fabricates assistant replies. Enter sends; Shift+Enter inserts a line break.

The assistant may return an answer with a draft-only proposal and/or contextual guidance. Render the answer and proposal as text, show the proposed morph values or appearance choices, and require the user to select **Apply to draft**. Applying uses the existing draft controls and save APIs; it does not invoke Blender, approve a plan, or compile. Compiled projects cannot receive appearance proposals, and unavailable morphs remain unavailable.

Guidance targets are stable, server-allowlisted identifiers for the morph library/control, eye or skin library/asset, preset library/asset, and workflow review area. On receipt, open the relevant category, scroll the target into view, and show a small dismissible tooltip pointing to that target. A slider-location question must open **Models → Body → Morphs**, select a real morph control, and explain where its amount slider appears—even when Copilot returns only plain text. Include a **Show guide** action in the assistant message so guidance can be reopened. If a target is not present, do not show a misplaced tooltip; report/retain the assistant message and allow a bounded retry while that editor content loads. Tooltips use ordinary escaped text, never model-provided HTML. The assistant must explain unsupported requests honestly; there is no installed age morph or aging-skin effect, so it may not promise a true aging transformation.

## States and capability boundaries

The interface distinguishes:

- Welcome screen, including API connection, saved-project loading, and error states; no model is loaded before an explicit project action.
- Explicit project create/open transitions into the character workspace; returning Home does not discard unsaved draft edits.
- No project selected versus an explicitly opened or newly created project.
- Plan awaiting approval, approved, draft autosave, Blender unavailable, and final compile in progress.
- Character draft and local preview versus assembled character, saved morph values, unsaved local edits, and baked geometry with its checkpoint-based restore action.
- Failed operations and recoverable saved project state.
- Copilot unavailable; no fabricated chat response.

Approval is required before final compilation in Blender; approval alone does not import geometry. Draft slider values, eye choices, preset choices, semantic skin properties, and skin paint strokes are project data, not saved Blender geometry. Eye previews use only the selected eye GLB and hide only the base preview's default eye meshes. For the compatible CC3+ Female skin, the viewport paint toolbar provides Paint/Erase, color, brush size, opacity, Undo stroke, and Clear paint. The brush ring follows the raycast hit on the head, body, arm, or leg; stylus pressure varies stroke size and opacity. Points are converted to normalized UV coordinates and persisted as bounded strokes, split when the UV path jumps, and composed on the browser preview without altering source maps. Painting disables camera orbit; the worker replays strokes onto copied full-resolution maps only during explicit final compile. Semantic layer management, alpha/scatter detail brushes, redo, and a synchronized 2D UV editor are not implemented yet. Skin tone, undertone, and roughness controls update the browser material preview immediately and require an explicit draft save. Deterministic freckles may be enabled for the head skin UV map and adjusted by density, size, strength, and color; this is not anatomically masked to the cheeks or nose. Copilot skin interpretation is reviewable and never applied or persisted without an explicit user action. Redness, moles, pores, wrinkles, subsurface controls, and region-specific effects are not supported yet. Component visibility changes affect only the current preview. Other unsupported categories, materials, markings, pose editing, and unsupported geometry operations remain unavailable. CC5/CC3+ preset selection previews and persists locally; final compile applies it to Blender. Never describe a preview-only edit as Blender geometry or imply that a placeholder is a real model.

## Object Workshop

Object Workshop is a separate browser-only workspace and does not change the character editor or start Blender. Its presets use bundled CC0 model bases for Chair, Stool, Table, Wall, and Shield; Cube remains a parametric primitive. The Wall preset remains a fixed straight masonry section from a modular fort asset. The separate Masonry generator creates bounded running-bond or stack-bond brick walls and paved roads from individual selectable pieces, with editable dimensions, joint width, subtle deterministic size/color variation, mortar or sand joint beds, clipped edge pieces, and optional paired right-angle wall-end returns. Moving an unlocked brick or paver snaps it to the unit grid; locking the assembly lets it move as one and prevents individual edits until unlocked. Generated layouts are capped at 350 pieces and scene validation bounds the saved component count. Model dimensions scale imported meshes while preserving their PBR materials, and the hierarchy exposes separate chair frame/upholstery, wall masonry/trim, and shield body/trim/hardware components where the source supports them. Source asset, author, and CC0 license links appear in the inspector. Newly added presets are placed clear of the existing scene, and older origin-stacked scenes are spread apart when loaded. The object hierarchy supports component selection, visibility/lock controls, duplication, deletion, and adding a simple custom box component. Components can be moved, rotated, scaled, assigned a material tint, and locally deformed using a draggable cage with adjustable resolution, influence, and X symmetry. An adjustable edge bevel remains available for the parametric Cube. Undo/redo, browser autosave, editable project JSON save/import, and scene GLB export are available.

The cage changes the selected procedural or imported component's actual preview vertices; it is not a visual-only handle mockup. Masonry variation is deterministic geometry/material variation, not texture displacement or physically simulated mortar; the generator currently supports rectangular walls/roads, running/stack bonds, clipped edges, and optional paired right-angle wall-end returns, not arbitrary drawn paths, curved or multi-segment corner layouts, herringbone, structural engineering, or Blender parity. The workshop remains an early modeling slice and does not yet support arbitrary topology editing, user-supplied model import, booleans, a general modifier stack, UV editing, rigging, or animation. Imported JSON is bounded and validated before replacing the current scene. Older local projects retain their original procedural components in a collapsed, hidden backup group and gain the matching sourced base; custom components and saved edits remain intact, and the previous base can be revealed from the hierarchy.

## Visual design

Use one midnight-slate theme throughout the workspace, project dialogs, and AI Assistant: base `#0e1118`, panels `#151a23`, raised surfaces `#1a202b`, primary text `#e7eaf0`, muted text `#9aa5b7`, and active blue `#438fff`. Keep success/warning/error colors reserved for status. Use restrained borders and consistent small radii. At desktop widths, preserve the 65px header, 109px labeled navigation rail, viewport, and editor proportions. Use compact spacing, visible focus, readable disabled states, reduced-motion support, and non-color status labels.
